# AI 推荐诊断与改进路线(对比主流 LLM 产品)

- 状态：评审文档(仅供讨论,未实施)
- 日期：2026-08-24
- 参照系：主流 LLM 产品(ChatGPT / 豆包 / Kimi 等)在"电影推荐"场景的做法
- 代码依据：`server/utils/agentRuntime.js`、`recommendCore.js`、`promptBudget.js`、`sessionSummary.js`、`llmClient.js`、`server/router/ai.js`、`router_handler/aiChat.js`、`client/src/components/AIRecommend.jsx`(行号为 2026-08-24 当前代码)

## 一句话结论

**骨架是亮点,产品是半成品。** "Tool-calling + grounding"的工程架子超出多数同类作业;但作为**推荐产品**缺了四个字——**recsys 化**:有生成没有检索、有个性没有记忆、有输出没有反馈、有运行没有评估。

## 一、主流产品做电影推荐应有的七件事 vs 现状

| 能力 | 主流产品做法 | 本项目现状(代码证据) | 差距 |
|---|---|---|---|
| 检索召回(第一跳) | 向量/规则召回后再排序 | 纯 LLM 文本排序,候选 ≤30(`recommendCore.js ~L150-161` 混合后 `slice(0,30)`) | 大 |
| 个性化(记忆) | 跨会话长期记忆 + 偏好持久化 | 仅会话级摘要(≤120 字、失败返旧),无用户偏好表 | 大 |
| 反馈闭环 | 点赞/踩/换一批 → 模型立刻修正 | 前后端均无反馈按钮/接口/落库(全库 grep 无 feedback 接口) | 大 |
| 冷启动 | 开场询问 + 流行兜底 + 明示"默认结果" | 无记录→画像 null(`recommendCore.js: if (!favoriteRows.length && !reviewRows.length) return null`),退化为通用高分且不说明 | 中 |
| 可解释性 | "因为你收藏了 X,所以推荐 Y" | `reason` 为 LLM 自由文本,无得分、无依据归属 | 中 |
| 评估 | 离线回测 / A/B / 命中率 | 仅 `movies_json/meta_json` 轨迹日志,无指标无回测 | 大 |
| 交互 | 停止生成 / 重试 / 修改要求 | 流式渲染,无停止/重试控件可见 | 中 |

## 二、缺陷清单(按"改进杠杆 × 成本"排序)

1. **无向量检索 / RAG(质量天花板)**
   `movies` 无 embedding 列、无任何向量工具,排序完全靠 LLM 文本输入约束(`recommendCore.js ~L254-259` 仅把候选清单塞进 system prompt)。"找像《XX》的片""上次那种感觉的片"这类语义召回做不了——相当于第一跳检索能力为零,后面排序再聪明也受候选池约束。

2. **候选池过小(第一跳把召回压到几十级)**
   单轮近/经典各 20 条、混合后截 30;agent 的 `search_tmdb` 固定 `page=1`、`limit` 钳制 1-20(`agentRuntime.js ~L400-414`);本地 `LIKE` 无全文索引。用户能"被看到"的片最多几十部,与主流产品动辄千级的候选池差距是本项目质量的最大瓶颈。

3. **无反馈闭环(推荐是"一锤子买卖")**
   前端零反馈控件,后端零反馈落库。主流产品允许"不喜欢这个导演/换一批/不要灾难片"并立即修正;本项目用户只能说"再来一次",模型无从学到"刚才那批不行"。

4. **无跨会话长期记忆(换会话等于失忆)**
   `sessionSummary.js` 只把 ≤120 字摘要注入**单次会话**的 system prompt,不进用户级画像;另开会话偏好归零。主流产品(如 ChatGPT 记忆)会把偏好沉淀为长期上下文。

5. **无冷启动策略**
   账号没收藏/评论时 `buildTasteProfile` 直接返回 null,推荐退化为"高分开场",且不告诉用户"这是默认结果、请先告诉我喜好"。主流产品靠开场提问或"探索式"内容引导冷启动。

6. **无评估设施(改 prompt 全靠手感)**
   `meta_json` 落了 agentTrace/sources,但无离线回测、无 A/B、无 hit-rate/NDCG。prompt 或候选池改动后有没有变好,没有任何可量化的判据——这是工程可信度最大的减分点。

7. **画像与排序脱耦(模型可以无视画像)**
   画像只作为文本提示进 system prompt,`profileApplied` 只是布尔标记(`agentRuntime.js ~L881`),**没有任何机制强制模型依据画像过滤候选**。结果:即使有画像,出片也可能跑题,且无法兜底校验。

8. **交互与成本**
   无停止生成/重试控件;本地 Ollama 串行推理,首 token 延迟与多轮成本偏高;无缓存;并且单轮 `POST /recommend` **无鉴权、无限流**(`server/router/ai.js L9`),仅 chat/chat/stream 挂了限流。

> 已具备、应保留的能力(不是缺陷):强制定 `plan_tasks` 与"计划内工具"约束(防模型乱调)、工具失败重试+降级链(LLM/TMDB 挂时回退本地片单)、SSE 真流式、prompt 字符预算、多轮会话摘要、chat 限流——工程骨架是过关的。

## 三、改进路线图(四个重心)

### A. 交互与反馈闭环(最直观,建议最先做)
- **A1 反馈按钮**:每个推荐卡片加 👍/👎/"换一批" → 新增 `ai_recommend_feedback(movie_id, action, session_id, created_at)` 落库；下轮注入"用户不喜欢《X》;换个导演"。低机动高感知。
- **A2 一句话依据**:卡片下显示规则生成的推荐依据(引用用户收藏/评论:"因为你收藏了《XX》"),不依赖 LLM 自由发挥,可解释且可控。
- **A3 停止/重试**:前端 `AbortController` 中断流式请求;出错的回合支持"重试"。
- 面试叙事:有反馈闭环才叫"推荐系统",一次性生成只是"聊天玩具"。

### B. 个性化质量(推荐效果的根)
- **B1 用户偏好持久层**:新增 `user_taste`(genre 权重、收藏时序衰减、点赞/踩累积)→ 跨会话注入 system prompt,解决"换会话失忆"。
- **B2 冷启动 2 问**:引导式开场("最近喜欢哪部?常看什么题材?")把答复转成初始画像;用户不答则用高分开局并**明示"热门兜底"**。
- **B3 两阶段结构(Retrieval→Rerank)**:规则召回(genre/导演/评分,放宽到 50-100 条)→ LLM 只在召回内 rerank,并加硬约束"≥60% 命中画像 top3 genre"。画像从"提示"变"约束",解决第 7 条脱耦。
- 面试叙事:Retrieval→Rerank 是行业通用形态,"把 LLM 当排序器而不是知识源"。

### C. 可评估性(让改进可证明)
- **C1 推荐事件日志**:展示/点击/👍/👎 全部落库(可复用 A1 表 + `hybrid_search_events` 同款思路)。
- **C2 离线回测**:用收藏+影评构造黄金集,计算 hit-rate@5 / NDCG;prompt、候选池、排序策略改版后跑同组回归,输出对比。
- 面试叙事:模型迭代"数能说话"。

### D. 性能与成本
- **D1 候选池扩容**:TMDB 多 page 抓取 + 把已交付的**豆瓣离线种子(246 部本地片)纳入召回池**,缓解候选过小且不依赖 TMDB 可达性。
- **D2 向量检索(可选二期)**:embedding 列 + MySQL 余弦近似,做语义召回;需要先解决 embedding 模型与存储选型。
- **D3 缓存**:热门意图/摘要结果缓存,降低重复多轮成本;给单轮 `/recommend` 补上鉴权与限流。
- 面试叙事:完整的 Retrieval→Rerank→Cache 工程链路。

## 四、与主流产品差距的总评(面试定位)

**刻意不做、可理直气壮**:多人协同过滤(UGC 冷启动建模)、实时 A/B 分流平台——演示项目做这个不划算,面试中可以明确说出"为什么不做"。

**必须补、否则简历只是"AI 玩具"**:召回 / 记忆 / 反馈 / 评估 四项。四项补齐后,项目即可表述为——**"生成式电影推荐系统的完整闭环:规则+向量召回 → LLM rerank 与 grounding → 反馈回流 → 离线回测"**,这是一个明显更高级的简历叙事,也覆盖了工程、算法、数据三条线的考核点。
